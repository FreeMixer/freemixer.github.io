Worked example: a third-party LV2 and CLAP plugin to a generated panel, adapted to Zynthian

This takes two plugins nobody here wrote, as a distribution installs them, through the whole panel path: the scan into a descriptor, the layout, the MOD GUI and the test that holds it to the descriptor. It then follows the LV2 one to where Zynthian looks for it.

  • LV2: ZamComp, Damien Zammit's mono compressor (urn:zamaudio:ZamComp), from Fedora's lv2-zam-plugins. Section 4 reads, from Zynthian's sources, where it would look for it.
  • CLAP: LSP Limiter Mono (in.lsp-plug.limiter_mono), from Fedora's lsp-plugins-clap.

Every command below was run as written, from the root of this repository, and its output is shown under it, or is the committed file it writes under examples/worked-example/. What each command printed is also committed, one file per command, in examples/worked-example/transcript/, written by repeat.sh (run it after the setup of the next section; a command that prints nothing leaves no file). The output shown here is that transcript, line for line. A [exit N] line is the command's exit status when it is not 0. The rpm -q and lv2ls lines and the package versions are those of the container the run was made in. Nothing here was run on a Zynthian or a MOD: the last section says what comes from Zynthian's sources and what is still to be seen on one.

Where it ran

A Fedora 44 container (the openmixer-worker image, whose packages the commands below upgrade), the Fedora repositories and the FreeMixer channel enabled. The image also carries a copr repository, which the installs leave out so that every plugin comes from Fedora itself. As root:

dnf -y -q --disablerepo=copr-ycollet-audinux install lv2-zam-plugins lsp-plugins-clap omx-clap-host plugin-hostd plugin-hostd-devel omx-contract-devel
dnf -y -q --disablerepo=copr-ycollet-audinux upgrade omx-contract omx-contract-devel omx-clap-host omx-clap-core plugin-hostd plugin-hostd-devel
ln -s "$PWD/bin/omx-panel.mjs" /usr/local/bin/omx-panel
dnf -y -q --disablerepo=copr-ycollet-audinux install omx-panel

and, as the user, npm ci --silent in this checkout.

On a stock Fedora 44, the OpenMixer channel comes first, as this repository's CI adds it (dnf install https://www.openmixer.org/rpm/openmixer-release.noarch.rpm; not run here, the image carries the channel), and python3-lilv and sord are installed with the rest (the image carries them: python3-lilv-0.26.4, sord-0.16.22, lv2-1.18.10).

omx-panel is this checkout, run as omx-panel through the link above (/usr/local/bin comes before /usr/bin on the path). The commands ran at 3ebf9b7, the commit that adds repeat.sh; its omx-panel is origin/main at 15cc25bb9 (pull request 26 merged, so the readout fix of omx-panel#25 is in), and the branch adds only the example, this document, a line of the README and the exemption of the example's output files in tools/check-spdx.mjs. The released omx-panel 0.2.5, installed last, is run as /usr/bin/omx-panel once: it stops on ZamComp (section 3). Every other command runs as an unprivileged user.

2. The scan into a descriptor

One step writes a scanned descriptor (omx-contract docs/descriptors.md) for either format: plugin-hostd-probe describe (plugin-hostd 0.7.0 and later, its docs/formats.md). It runs omx-clap-core's omx-clap-scan --fields, the dump of every field one CLAP or LV2 plugin states, read as a host reads it (for LV2, through lilv), and maps each field to a descriptor word by plugin-hostd's format tables. So the LV2 scan to a descriptor exists, and it is the same step as the CLAP one.

$ rpm -q omx-clap-host omx-clap-core plugin-hostd omx-contract
omx-clap-host-0.20.1-1.fc44.x86_64
omx-clap-core-0.20.1-1.fc44.x86_64
plugin-hostd-0.10.0-1.fc44.x86_64
omx-contract-3.1.0-1.fc44.noarch

$ omx-clap-scan --fields lv2:urn:zamaudio:ZamComp > examples/worked-example/zamcomp/zamcomp.fields.tsv

$ plugin-hostd-probe describe lv2:urn:zamaudio:ZamComp > examples/worked-example/zamcomp/zamcomp.descriptor.json

$ omx-clap-scan --fields clap:/usr/lib64/clap/lsp-plugins.clap#in.lsp-plug.limiter_mono > examples/worked-example/lsp-limiter-mono/limiter_mono.fields.tsv

$ plugin-hostd-probe describe clap:/usr/lib64/clap/lsp-plugins.clap#in.lsp-plug.limiter_mono > examples/worked-example/lsp-limiter-mono/limiter_mono.descriptor.json

The dumps are the committed .fields.tsv files, the descriptors the .descriptor.json beside them. What a scan cannot know, it writes as unknown:

  • every control's meaning is unknown (neither format states what a control means), so the layout infers no family and no roles: both plugins are family none;
  • ZamComp's units are its TTL's (ms, dB), its rat and slew state none (unknown); gr and outlevel are readonly, with a range and no default;
  • the limiter's controls are keyed by CLAP parameter id, a number; their units are unknown and their scales unknown or stepped, as CLAP states neither.

The limiter's 28 controls state no group, so they are one section Controls, four pages of eight, the last holding four (limiter_mono.pages.json, each slot a CLAP parameter id). These are the pages a CLAP host shows through clap.remote-controls. A MOD GUI belongs to an LV2 bundle, so the generator refuses a CLAP descriptor by name; lsp-plugins also ships an LV2 build, which would be scanned as lv2:<uri> and go the way of ZamComp.

4. Zynthian

What follows comes from Zynthian's sources (zynthian-ui f46b018 and zynthian-sys 0774a58, both on their vangelis branch; zynthian-plugins 648c84a, its master), the omx-plugins README, and the lilv runs shown. Each file and line cited is at those commits. None of it was seen on a Zynthian.

Where Zynthian looks for LV2 bundles and their MOD GUIs

  • LV2_PATH is /usr/lib/lv2:/usr/lib/arm-linux-gnueabihf/lv2:/usr/local/lib/lv2:$ZYNTHIAN_PLUGINS_DIR/lv2: $ZYNTHIAN_DATA_DIR/presets/lv2:$ZYNTHIAN_MY_DATA_DIR/presets/lv2 (zynthian-sys scripts/zynthian_envars.sh:107), with ZYNTHIAN_PLUGINS_DIR /zynthian/zynthian-plugins (:105). zynthian-ui loads it with lilv's world.load_all() (zyngine/zynthian_lv2.py:213).
  • A bundle a user adds goes to /zynthian/zynthian-plugins/lv2 (LV2_DIR, zynthian_lv2.py:197): the webconf upload copies it there through add_engine (zynthian_lv2.py:386), and the omx-plugins README has a Zynthian without the apt channel copy its lv2/ bundles there and rescan the LV2 plugins from the admin menu. A plugin the rescan finds for the first time is disabled until enabled (zynthian_lv2.py:619).
  • The last commit of the zynthian-plugins repository (directories dssi, ladspa, lv2, vst) is 648c84a, dated 2016-09-21. The image's setup script installs LV2 plugins with apt-get, and the list names zam-plugins (zynthian-sys scripts/setup_plugins_rbpi.sh:42-52, the name on line 52); the recipe that builds zam-plugins from source, scripts/recipes/install_zam.sh, is commented out at setup_plugins_rbpi.sh:94. That the Debian package carries the same ZamComp as Fedora's, and puts it in /usr/lib/lv2, is not read from these sources.
  • A MOD GUI is drawn by MOD-UI, which Zynthian runs as an engine of its own (zynthian-ui zyngine/zynthian_engine_modui.py; zynthian's mod-ui fork, scripts/recipes/install_mod-ui.sh, run by setup_system_raspioslite_64bit_trixie.sh:562). Its service takes an LV2_PATH (etc/systemd/mod-ui.service:11) that scripts/update_zynthian_sys.sh:527 fills from the value set at :188: the same directories as above plus /usr/lib/$arch_libdir/lv2 and $ZYNTHIAN_PLUGINS_DIR/lv2-presets.

On a Zynthian where the Debian package has put ZamComp in /usr/lib/lv2/ZamComp.lv2 (not read from the sources, see above), that bundle is first on LV2_PATH, and a copy of the bundle in /zynthian/zynthian-plugins/lv2 would be ignored by lilv as above. add_engine refuses a plugin whose engine is already registered unless force is set (zynthian_lv2.py:411-424). The MOD GUI then goes into the bundle lilv takes: copy modgui.ttl and modgui/ from examples/worked-example/zamcomp/with-panel/ZamComp.lv2/ into /usr/lib/lv2/ZamComp.lv2/, append the same rdfs:seeAlso line to its manifest.ttl, and restart MOD-UI. That step was not run, and a zam-plugins upgrade would overwrite the manifest. The descriptor should be the scan of the Zynthian's own ZamComp, whose Debian version may differ from Fedora's 4.4.

What the encoder pages show

The pages of eight above are the layout's: what a CLAP host shows through clap.remote-controls. Zynthian's touchscreen does not read them. For an LV2 plugin hosted by jalv it builds its own screens of four (zynthian-ui zyngine/zynthian_engine.py, generate_ctrl_screens, lines 681 to 724):

  • the controls are the plugin's input control ports, in port order (zynthian_lv2.py:940, get_plugin_ports), sorted by lv2:displayPriority, and grouped by pg:group; ungrouped controls are the group Params;
  • each group is cut into screens of four, numbered from 1 when a group has more than four;
  • an audio effect with no bypass port of its own gets a bypass control, added last (zyngine/zynthian_engine_jalv.py:544);
  • output control ports are no controllers: a readout is never on a screen.

ZamComp states no port group and no display priority:

$ grep -c -E 'portgroups|pg:group|displayPriority' /usr/lib64/lv2/ZamComp.lv2/ZamComp_dsp.ttl
0
[exit 1]

So, by those rules, Zynthian shows ZamComp as Params 1 (Attack, Release, Knee, Ratio), Params 2 (Threshold, Makeup, Slew, Sidechain) and Params 3 (bypass), and neither gr nor outlevel. This is read from the source, not seen. The layout's sections do not reach Zynthian's screens: an LV2 bundle would carry them as pg:group in its TTL, which the MOD GUI generator does not write. The word clap appears in no file of zynthian-ui at f46b018 (grep -ri clap finds nothing), and in zynthian-sys at 0774a58 only once, in a name misspelt "Claption" in a plugin description (config/engine_config.json:7932), so those sources name no CLAP host or plugin and the limiter's pages are not shown there.

What is verified, and what is not

Verified, by the commands above: both plugins come from Fedora 44's own packages; plugin-hostd-probe describe writes a scanned descriptor of each; omx-panel layout lays out ZamComp with and without a panel file and the limiter, and stops on Filter Mono and three more of the 63 mono lsp plugins (omx-panel#27); omx-panel modgui writes ZamComp's MOD GUI with and without a panel file, each bundle passing tools/modgui-test.sh, and refuses the CLAP limiter by name; omx-panel 0.2.5 stops on ZamComp's readout (omx-panel#25); lilv reads the MOD GUI from a copy of the bundle once its manifest names modgui.ttl, and keeps the first of two bundles of one plugin on LV2_PATH.

Not verified:

  • anything on a Zynthian or a MOD: the bundle's install there, MOD-UI drawing the template, the screens of four, the rescan;
  • the template as mod-ui draws it in a browser: the tests read the template's text and its TTL, not a render;
  • the readouts' displays showing a value: the generated MOD GUI draws a frame, and a live reading needs a modgui:javascript, which is not generated (docs/modgui.md);
  • ZamComp's Debian build (Zynthian's) having the same ports as Fedora's;
  • the limiter's pages on a CLAP host with a controller.
