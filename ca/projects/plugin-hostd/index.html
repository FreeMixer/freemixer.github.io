plugin-hostd

plugin-hostd runs your LV2 and CLAP audio plugins, each in a worker process of its own, and puts back any worker that dies. A plugin that crashes takes down its own worker and nothing else. It is for anyone who runs plugins live on Linux, on a mixing console, a stage rig or a Raspberry Pi, and cannot let one bad plugin stop the show.

  • A crash stays small: only the plugin's worker is lost, and it is respawned with the links the daemon made itself.
  • Nothing to change in your controller: it speaks mod-host's socket protocol, same ports, same replies.
  • LV2 through omx-clap-host's adapter, with mod-host for the plugins the adapter refuses, and CLAP through omx-clap-host, side by side.
  • Audio never passes through the daemon; every worker is a JACK client, as in mod-host.
  • A plugin that keeps crashing is singled out and given up on without touching its neighbours.

Three things it adds, each optional and taken or left on its own:

  • Plugin hosting: the LV2 and CLAP plugins hosted in workers, with a qualification on the device saying which are safe to load and how.
  • Grouping: a controller's chain stays as it is; when several of its plugins may share one process, by their records, they run in one worker, and the others alone.
  • Panels: a plugin's control pages and its MOD GUI drawn from its one description, with omx-panel; a plugin's own GUI is kept.

Install

Fedora:

sudo dnf install https://www.openmixer.org/rpm/openmixer-release.noarch.rpm
sudo dnf install plugin-hostd omx-clap-host

Debian bookworm and trixie and Raspberry Pi OS (amd64 and arm64):

curl -fsSLO https://www.openmixer.org/deb/openmixer-release.deb && sudo apt install ./openmixer-release.deb
sudo apt update && sudo apt install plugin-hostd omx-clap-host

The LV2 worker is mod-host, which Debian does not package; without it CLAP plugins still work.

Status

What the continuous integration runs on every push:

  • The daemon against stand-in workers that die on cue: placement, forwarding, the ledger, replay, attribution and the bound on a respawn storm. No JACK and no plugin are needed for this.
  • The generated protocol files, README tables and man page checked against protocol.h, and every guard broken on purpose to see its test go red.
  • The daemon with a real CLAP worker (omx-clap-host) over PipeWire's JACK and over JACK2's jackd, including meters reaching the controller.
  • RPMs (Fedora 44) and DEBs (bookworm and trixie) built and installed in a clean environment.

The LV2 worker (mod-host) is not run in CI; those steps stay in the Makefile for a machine that has mod-host and an LV2 bundle.

Try it

Start the daemon, with pin checking off for a first try (it says when both ports accept):

echo 'require_pins 0' > plugin-hostd.conf
plugin-hostd -n -p 5555 -c plugin-hostd.conf

In another terminal, add an LV2 plugin, set its gain and ask where it runs (messages end in a NUL byte, which printf adds):

send() { printf '%s\0' "$1" | nc -w3 127.0.0.1 5555 | tr '\0' '\n'; }
send "add http://plugin.org.uk/swh-plugins/amp 0"      # resp 0
send "param_set 0 gain 6"                              # resp 0
send "param_get 0 gain"                                # resp 0 6.0000
send "worker_list"                                     # resp 1 w1:<pid>:lv2:up:1:qualified:own:0

The plugin now runs as JACK client effect_0 in its own process. Link it in your graph as you would a mod-host plugin. man plugin-hostd has the options; the full protocol is below.

Using it from your own host (Zynthian, a Raspberry Pi, any Debian): docs/own-host.md, nine commands from nothing to a plugin running.

Under Zynthian on a Raspberry Pi 5: https://openmixer.org/docs/zynthian says what it changes, how to install and use it and where it stands; the measurements are at https://openmixer.org/benchmarks, and how they were taken, with the design of pins, chains and grouping, in the technical notes at https://openmixer.org/notes.

Building from source: see BUILDING.md. More about FreeMixer at https://www.openmixer.org.

Protocol

The protocol is the plugin-hostd protocol, a superset of mod-host's text protocol: any mod-host client works unchanged. It is declared once, in plugin-hostd-protocol, the library the daemon answers its controllers with; the wire protocol for a reader of another host, mod-host's verbs on plugin-hostd and the verbs mod-host does not have, is its doc/protocol.md.

What it declares is installed with that library's development package (plugin-hostd-protocol-devel, libplugin-hostd-protocol-dev): the header <plugin-hostd/protocol.h> with the placement syntax, the error codes, the feedback events, the settings and the verbs (pkg-config --cflags plugin-hostd-protocol); the one verb table, its grammar, and the protocol and mod-host's as JSON (pkg-config --variable=table, grammar, protocoljson and modhostjson of plugin-hostd-protocol). The verbs the daemon adds are its package of omx-contract's contract directory (plugin-hostd-protocol-contract). A refusal number omx-clap-host answers too carries omx-clap-core's reply.host.* code (package omx-clap-core-contract), the others plugin-hostd's reply.plugin-hostd.*: one name per number. The tables here and the man page's key list are generated from that header; this tree keeps no copy of it.

This tree's development package installs what it declares beside the protocol: the schemas probe-output.schema.json for the probe's document and preset.schema.json for the org.openmixer.preset file (protocoldir in the pkg-config file of plugin-hostd is that directory), and <plugin-hostd/pin.h>.

Running

plugin-hostd -n -p <port> [-f <port>] [-c plugin-hostd.conf]

It prints plugin-hostd ready! once both ports accept.

No worker exists until the first add. quit or SIGTERM stops every worker and the daemon; after a SIGKILL the workers notice the parent gone (PR_SET_PDEATHSIG) and exit.

Both ports listen on 127.0.0.1, so only programs on the same machine reach them. To control the daemon from another machine, start it with --bind-address <address> or set bind_address in the settings; 0.0.0.0 is every address of the machine. A controller is not authenticated and can load a plugin from any path, so do that only on a network whose hosts you trust. A daemon that cannot listen on the address does not start. The workers it starts listen on 127.0.0.1 whatever this says, and only the daemon talks to them.

Placement

The placement of an add is own | pool:<name> | chain:<chain> | default. own is a worker for that instance alone; pool:<name> is the pool's worker, opened on first use and capped by pool_config, and a full pool opens <name>#2, <name>#3, and so on; default is the policy of policy_set. A pool name matches ^[A-Za-z0-9_-]{1,32}$.

<uri> is lv2:<uri> or a bare URI for an LV2 plugin, clap:<path>#<id> for a CLAP one. The instance number is the controller's and reaches the worker unchanged. A worker holds one format. An own LV2 worker sees one bundle: LV2_PATH is a directory of the daemon's holding a link to the bundle whose manifest.ttl names the URI.

A token after the instance that is not a placement is the fork's optional jack client name, passed on. An instance that crashed in a pool is placed own whatever the hint until quarantine_clear.

Grouped workers against one process per plugin

A chain runs its plugins in one worker; the other way is one process per plugin. One measurement of the two, with 16 plugins, with the numbers of the page at https://www.openmixer.org/docs/grouped-vs-processes:

grouped one process per plugin
resident memory (RSS), 48 kHz 125.4 MB 1764.6 MB 14x smaller grouped
proportional memory (PSS), 48 kHz 42.9 MB 118.2 MB 2.8x smaller grouped
  • RSS counts a shared library once for every process that maps it, so a design with many processes looks larger than it is. PSS divides shared pages between the processes that use them, so it is the honest figure. Do not read the RSS ratio as the saving in real memory.
  • CPU: 1.2 to 1.9x less when grouped, across 3, 8 and 16 plugins at 48 and 96 kHz.
  • Context switches: up to about 14x fewer when grouped, 13.9x at 48 kHz and 14.8x at 96 kHz with 16 plugins.
  • Xruns over the 12 runs of each mode: 10 grouped against 41 with one process per plugin. Each run is one window of 10 seconds and the xruns in it are few and unevenly spread, so the 10 against 41 is suggestive and not proof.

How: a Raspberry Pi 5 with 4 cores, CPU governor on performance during the runs, plugin-hostd 0.12.0 with omx-clap-host 0.22.1 as the worker, N omx plugins in series, 256 frames, on a private JACK server.

Not measured: only 256 frames; only plugin-hostd, with omx plugins; the grouping planner is not part of the result and no default has been changed because of the numbers; DSP load and xruns are those of the JACK dummy driver, so no claim about real audio hardware is made.

A <state> is up (accepting commands), starting (spawned, not yet accepting), backoff (dead, waiting to be respawned), given-up (the storm bound is spent for its placement).

A record's place holds a colon (pool:p), so a worker_list record is read from both ends: six fields on the left, the instance list on the right, the place in between. The fifth is the audio core the setting placement pinned the worker to, - for none (docs/placement.md). The sixth is the worker's thread pool: on for a worker started with --thread-pool=on, which only a CLAP or lv2-clap worker of one plugin whose pin carries pool=cores is, qualified for every other (the worker's default, which grants the pool to no plugin).

panel_get gives a host that draws a plugin's panel itself (Zynthian's engine, a console) the panel the plugin publishes, as the scan of its add read it: sections, controls with their widget and visibility rule, roles, displays and placement defaults. What a host knows of a strip and of a plugin's controls. For a CLAP instance the daemon routes them like mod-host's instance verbs and passes the worker's reply through; the worker answers them from the plugin (clap.track-info, clap.remote-controls, clap.params), except param_info: omx-clap-host answers it from the param contract (org.openmixer.param-contract/1), and -511 for a parameter the worker holds no checked contract for (and -103 for a symbol that is no parameter). -511 is the stable answer to read as "no contract; fall back to the layout from omx-clap-scan"; the daemon passes it through and drops nothing. For an LV2 instance on mod-host the daemon answers them itself, never forwarding them, so mod-host learns none of them: track_info is kept and answered resp 0, and the other two come from the bundle's Turtle, read when they are asked (the manifest and the files it names with rdfs:seeAlso). remote_pages and remote_page_get make a page of each pg:group's control inputs in port order (the group's lv2:name, else its rdfs:label; a further page, "Name 2", for each 8 past the first), one page named Controls for the control inputs in no group, the pages in the order their group first appears; outputs and pprops:notOnGUI ports are on no page, a slot is the port's symbol, and the section is empty. param_info answers a control port from its own statements: its units:unit (the words of data/formats/lv2.json, empty for a port with none), stepped for an integer, toggled or enumeration port, log for a pprops:logarithmic port whose bounds are positive and linear otherwise, its lv2:minimum, lv2:maximum and lv2:default (a toggled port's are 0, 1 and 0 when it states none), a step of 1 for a stepped port and 0 for the others, and its symbol. -511 stays the answer for a port with a unit the table has no word for (a unit of the plugin's own) or no range, and -103 for a symbol that is no control port. A bundle the daemon cannot find or read has no pages, and param_info asks mod-host as it did. When a CLAP plugin changes its pages, its worker writes remote_pages_changed <instance> on its feedback port and the daemon relays it.

Notes are played the same way, by a controller that is not a jack client (a web console, a test, a MIDI surface on the network): note_input says whether an instance takes notes, and note_on, note_off and all_notes_off reach its worker unchanged once the daemon has checked their words. The workers' own feedback

What a worker reports on its feedback port (the output_set of a monitored output, the param_set of a parameter the plugin moved, data_finish, the log lines) reaches the controller on the daemon's feedback port, among the events above:

Every worker is started as <program> -n -p <command port> -f <feedback port>.

  • every line a worker writes on its feedback port goes out on the daemon's feedback port as the worker wrote it: output_set, param_set, data_finish and the rest of mod-host's feedback, and a line the daemon does not know.
  • the instance number in a relayed line is already the controller's: add hands it to the worker unchanged, so nothing in a line is rewritten.
  • a worker's lines go out in the order it wrote them, and what a worker wrote before it died goes out before its worker_died event; an instance lives in one worker at a time, so its lines keep their order across a respawn; the lines of different workers interleave.
  • monitor_output is in the ledger, one line per output, and param_monitor as it was sent; a respawn replays them after the add, so a respawned instance reports the same outputs, each once, starting again from its first value.
  • output_data_ready names no instance and goes to every worker; each worker's data_finish is relayed.
  • with no feedback port, or no controller on it, a line is dropped, as mod-host drops it; the daemon reads every worker's feedback all the time, so no worker waits on it.

A synced delay or an arpeggiator comes back at the right tempo after a crash. What the daemon keeps of the commands every worker shares:

  • the tempo, the metre and the transport a controller sets (mod-host's set_bpm, set_bpb, transport and transport_sync) are kept, the latest line of each as it was sent, in the order they were last sent.
  • a worker is handed them before anything else: a respawned one before its first add, and a worker started later, of a new placement, as well; a worker's refusal of one is written to stderr and is no failure.
  • a line whose words are not that command's grammar is passed on and not kept.

Probing a plugin

plugin-hostd-probe run loads a plugin in a child process under limits and writes down what happened, as facts only: no verdict. The child is clap-qualify for a CLAP plugin. For an LV2 plugin, named lv2:<uri>, the child is plugin-qualify's lv2_measure, found at run time in /usr/libexec/plugin-qualify (plugin-qualify is not a dependency of this package). The runner never loads plugin code itself.

plugin-hostd-probe run --out probe.json --log probe.stderr.log /usr/lib64/clap/plate.clap org.example.plate
plugin-hostd-probe run --out probe.json lv2:http://example.org/plate

A CLAP instrument is timed holding notes down: as many as the voice capacity it declares, or, when it declares none, the count --probe-notes N gives; --hold N holds that count whatever it declares. Both are passed to clap-qualify. Each rate's grid point carries the cost clap-qualify timed at that rate, in nanoseconds per sample, and for an instrument voices, the notes it held and why that many (declared or probe). A rate it did not time has no cost. An instrument has no input for the impulse, so its latency is measured from a note (method: note-onset), with heard: false at a rate where the note did not sound.

clap-qualify runs under plugin-qualify's interposer, rt_interpose.so beside the child. A bare --child is found as execvp finds it; name the child by path when PATH is unset or holds a directory of its name. The measured child gets the interposer and nothing else: an LD_PRELOAD the runner was started with is dropped for the measurement, named in run.tools.droppedPreload and in the rt-safety step, and put back in the runner's environment after the child. The first grid point carries what process() did under it, and an instrument's note sweep carries what process() did while notes played. run.tools.interposer names it once the child says it counted under it. With no interposer beside the child, or one that did not load, no count is written: rtSafety says interposer: false, and the rt-safety and note-sweep steps are probe.not-attempted and say why.

An LV2 plugin is measured the way plugin-qualify's LV2 hosting pass measures it, in two children under the same limits and the same wall clock. The first child (lv2_measure --pin) pins the bundle's files without instantiating the plugin. The second measures at the highest of --rates, in blocks of --quantum, with 30 instantiate and destroy cycles and 3 swept rt-safety runs. It runs under plugin-qualify's interposer (rt_interpose.so beside the child, found and with any other preload dropped as for clap-qualify) and the noise stimulus. The document's binary is the plugin's library, with every pinned file of the bundle listed. The rate's grid point carries what run() did under the interposer and, for a plugin with a MIDI input, its note sweep (what run() did while notes played), and behaviour carries the lifecycles, the threads and the features the plugin requires. A plugin no bundle holds exits 3 with no document. A plugin of which nothing could be pinned exits 2 with no document, because the document has no binary to name. Its refusal is a code on stderr: <plugin>: <code>: <why>, probe.unpinnable for a bundle the pin cannot cover. Version 1 runs the quick measurement only: the deep lifecycle pass and the soak stay plugin-qualify's until the probe protocol says which plugins get them and for how long.

The runner kills the whole process tree of the child at its wall clock, and again when the child is done, so a process a plugin started in a session of its own does not outlive the run. It applies these limits on every Linux: the wall clock, the CPU time, the memory, the open files, the file size, no core dump, the real-time priority it was granted and the wall budget as its real-time CPU time, the memory it may lock, no new privileges, the child dying with the runner, and the cpus the child may use (--cpus). --list-limits prints them as a run on this machine would apply them.

The measured child runs as the host runs the plugin: SCHED_FIFO at the highest priority the runner may give it (all of it with CAP_SYS_NICE, else the RLIMIT_RTPRIO hard limit the runner was started with, else none), with its memory locked by the runner's lock preload (<libexecdir>/plugin-hostd/probe-lock.so, /usr/libexec in the packages, beside the interposer) when its RLIMIT_MEMLOCK covers the memory limit. The runner itself and an LV2 plugin's pin pass stay SCHED_OTHER. run.realtime says what the kernel reported for the child after the exec (class, priority, the priority requested, who granted it, and why none), capabilityBound (whether the child, as the kernel reports it, holds no capability in its permitted or effective set, so it cannot raise RLIMIT_RTPRIO, RLIMIT_RTTIME or RLIMIT_MEMLOCK again: the probe drops every capability and the bounding set, which a runner without CAP_SETPCAP cannot, and then it says false), offer.realtime is that class, and run.memoryLock says whether the lock held. A service that runs the probe passes the grant with LimitRTPRIO= and LimitMEMLOCK= (docs/own-host.md). A limit the set asks for and this version does not apply (the number of tasks, namespaces, Landlock, seccomp) is listed in the document under limits.unavailable with its code, and --require tasks makes the run refuse instead.

The memory limit (--data-bytes) is memory.max of a cgroup the measured child runs in, so the kernel counts what the plugin really holds and kills its whole tree at the limit; that run ends probe.memory-limit, with the limit in the step's detail and the document written as for any other outcome. The cgroup goes under the runner's own cgroup when that hands the memory controller down, else beside it, else, when the runner is alone in a delegated cgroup, under it once the runner has stepped into a leaf; it is removed after the run. A machine that gives none of these bounds the child with RLIMIT_DATA, and limits.unavailable says so: memory with probe.limit.cgroup-absent (no cgroup v2 hierarchy) or probe.limit.controller-not-delegated. Children other than the measured one always run under RLIMIT_DATA.

A plugin's footprint, when the child took one, is the point's memory: how far the resident set grew from before the plugin loaded, in KB, after instantiate, after activate, at rest after processing, with notes held, and what a second instance added. A figure the child could not take is absent, and unmeasuredReason says why when none could be.

A crash, a hang and a timeout are outcomes in the document, never a missing document: the steps the child finished before dying stay in it. The exit status says whether there is one: 0 a complete run, 1 a document with some step that ended otherwise, 2 no document, 3 no such plugin. The document is described by probe-output.schema.json, generated from the codes in protocol.h, and installed with the protocol.

Pins

Why: a plugin is checked before the console trusts it. We measure one build of it for crashes, real-time safety and its parameters. The pin makes sure the bytes that load are the bytes that were checked, so an update or a swapped file cannot slip in unchecked. The layout pin also protects the controls: presets, surfaces and the REST rows are mapped to the plugin's parameters, and a changed layout would send values to the wrong ones. It also leaves a record you can audit: the exact plugin build that processed the audio.

With require_pins on, the default, add admits only a plugin that has a pin: the SHA-256 of every file the host loads for it, and its parameter layout fingerprint. Before any worker is spawned or sees the add, the daemon hashes each pinned file over one open descriptor: for a CLAP the files beside the .clap that clap:<path>#<id> names, the .clap itself among them; for an LV2 the files of the bundle whose manifest.ttl names the URI, the manifest among them, and every file the manifest names with lv2:binary or rdfs:seeAlso for the plugin must be held by the pin. No pin, or a layout pin in a scheme this version does not know, answers PHD_ERR_PIN_ABSENT; a file missing, changed or not held answers PHD_ERR_PIN_BINARY_MISMATCH. For a CLAP the daemon then sends the worker pin_expect <instance> <layout pin> and the add unchanged, and the worker answers PHD_ERR_PIN_LAYOUT_MISMATCH when the layout after init is not the pinned one; a worker that refuses pin_expect gets no add, and its refusal is the reply, and one that dies on it or does not answer it is dropped with PHD_ERR_VERB_DROPPED, the instance_verb_dropped event naming the pin_expect. An LV2 worker gets no pin verb: its layout is its bundle's TTL, which the hash covers, in a world of that one bundle; so a pinned LV2 plugin gets a worker of its own, a default that resolves to a pool is placed own and an explicit pool:<name> answers PHD_ERR_PLACEMENT_INVALID.

Where the pin comes from is pin_mode. strict takes it from pin_set or from a pin_file loaded at start, and a plugin with no pin is refused. first-use, the default, records it: the first add of a plugin with no pin hashes its files, keeps the pin in the pin store ($XDG_STATE_HOME/plugin-hostd/pins) and places the instance own; the layout is asked of the worker after the add (pin_layout) and recorded too. A host that pins by itself sets pin_mode strict. The store, a pin_file and pin_set carry one line format, pin_set <uri> <files> <layout> [verdict=<word>] with the verb optional in a file. In first-use only a pin with verdict=in-process, which plugin-qualify writes, lets a plugin share a worker. A pin with verdict=refused names files that failed qualification. Their add answers -516 (PIN_REFUSED), no worker sees it, and a replay is refused with the same code. A pin that changes to refused while the instance runs takes effect at its next replay. Files that differ from the pin answer -509 first, because the verdict was given for the pinned files only.

The pins are read again while the daemon runs, so a plugin upgrade never needs a restart (#255). The daemon stats the pin_file and the pins_dir files at every idle tick and before every add, and reads them again when one changed (a rewrite in place or a rename over it); pin_reload, and the sync's pin_changed notice, do the same at once. The new tables are put in whole or not at all: a pin_file with a line outside the grammar answers -902 and the earlier pins hold. A pin_set of a controller is not in any file and is kept. Running instances keep running: one whose files the new pins refuse is logged on stderr, and its id in worker_list is followed by ! until a pin holds it again. A plugin that changed since it was pinned is refused (-509, or -510 from the worker), the pin_changed <uri> files|layout event names what changed, and pin_accept <uri> takes the new pin.

Pins that ship with packages live in a read-only layer of their own, under the host's. At start the daemon reads every *.pins file of pins_dir (/usr/share/plugin-hostd/pins.d by default; empty is none), in byte order of their names, in the same line format. A package drops its own file there, so its plugins and their pins are replaced in one transaction and removed together; plugin-hostd owns the directory and another package may co-own it. The daemon never writes it. A pin from this layer is trusted as it is, in both pin modes. The rules:

  • A pins.d pin with verdict=refused always holds. The pin store, a pin_file and pin_set never override it: pin_set and pin_accept of its uri answer -516 (PIN_REFUSED), and a line of the store or of the pin_file for it is kept but has no effect, which stderr says at start.
  • Any other pins.d pin is under the host's layer. A pin of the same uri in the store, the pin_file or from pin_set holds over it, and pin_accept of a plugin whose files differ from its package pin records the new files in the store, which then hold. pin_clear forgets the host's pin only: the package pin holds again.
  • When two pins.d files hold the same uri, a refusal wins; otherwise the file last in name order wins. Two lines of one file follow the same rule, the later line in place of the later file.
  • A line outside the grammar, or longer than a pin line can be, is skipped and named on stderr; the rest of the file is read. A file that cannot be read is named on stderr and skipped. A directory that is missing or empty holds no pins and is no error.

What cannot be pinned:

  • a path holding ',', '=' or whitespace cannot be pinned: they are the separators of pin_set's words, and pin_set refuses it as a token outside its grammar.
  • a pin_set line is at most line_max, 4096 bytes, the protocol socket's buffer; a longer one is refused as outside the grammar.
  • a manifest that uses @base makes add answer OMX_REPLY_PLUGIN_HOSTD_PIN_BINARY_MISMATCH_RESP (-509): the daemon does not resolve it, so it cannot know the file the host would load. A file the manifest names by a percent-encoded IRI is pinned as written, one word, and opened decoded; a name with a stray % is refused the same way.

Pins are the controller's policy, like policy_set: not in the ledger, gone with the daemon, set again by a controller that reconnects. A replayed add is checked again, so a file swapped while a worker was down is refused on respawn: the daemon emits instance_replay_refused <instance> <code> with the refusal's own code (the pin's, or the worker's when it refuses the replayed pin_expect or add), writes PHD_ERR_REPLAY, the step and that code to stderr, and the worker does not hold that instance until a later replay passes. The hashing and the layout serialisation are include/plugin-hostd/pin.h, installed beside the protocol header for the hosts that check a layout.

The running history

The daemon keeps what each plugin did on this machine, per plugin, per binary and per host class: the file named by history_file, else $XDG_STATE_HOME/plugin-hostd/history, else $HOME/.local/state/plugin-hostd/history. It is local: it holds URIs, digests and counters, no audio, no path, no user, session or preset name, the daemon sends it nowhere and no verb writes it from outside; history_clear <uri | all> deletes it. Only the daemon writes it, mode 0600 in a directory of mode 0700, to a temporary file that is renamed over it, at most once per history_save_s and at quit. history_window_s 0 keeps none.

The first line is # plugin-hostd history/1, then one line per key, history <uri> <binary digest> <host class> key=value .... The binary digest is the SHA-256 of the first file the plugin's pin holds, so a plugin with no pin has no history and a changed plugin starts a record of its own, the old one kept and not read. The host class is arch/cores/clock as the probe writes it (x86_64/5-8/2.5-3.5GHz), or the host_class setting. The keys are the words of PLUGIN_HOSTD_HISTORY_KEYS in data/history.json: first, last, windows_solo, windows_grouped, cpu_p95_solo, cpu_max_solo, pss_mb_solo, xrun_windows_solo, xrun_windows_grouped, crashes_solo, crashes_grouped, restarts_grouped, quarantines, last_crash, last_crash_grouped.

A window is history_window_s seconds of one worker: its utime plus stime from /proc/<pid>/stat as percent of one core, and the Pss of its smaps_rollup. A worker of its own gives a window to the plugin it holds; a worker of two or more gives one to each member, counted in windows_grouped and nowhere else, because a group's CPU cannot be split among its members. cpu_p95_solo is an estimate that needs no list of windows: each window above it moves it up by 0.95 of 2 percent of itself and each one not above moves it down by 0.05 of that. A window in which the members of the worker changed is dropped, and a worker that died is counted if it had been up for half the window. A crash is counted when the daemon names a culprit (crashes_solo in a worker of its own, crashes_grouped in a group), the members that went down with it and were not the culprit get restarts_grouped, and a quarantine counts in quarantines. A worker writes xruns <count> on its feedback port, the JACK xruns it has counted since it started, when the count changes. The daemon takes the first count of a process as its baseline, never as xruns of the window it arrives in, and at the close of a window adds one to xrun_windows_solo or xrun_windows_grouped of every member of the worker when the count rose in it, however many xruns it rose by. A worker that wrote no count counted none; a restarted worker counts from zero and its first count is a baseline again; a line that is not the word and one whole number is not a count.

A line this version cannot read, or with a key it does not know, is kept as it is by every save and is not read. A file that cannot be read, or whose first line is another version, is neither read nor overwritten: stderr says why, and history_get answers unavailable until the file is repaired or removed.

history_get <uri> answers the record of the binary the pin holds now, on this host class, as one word: digest=, class=, crashed=1 when a crash is within 30 days, raises_xruns=1 when the share of xrun windows in a group exceeds the share alone by 5 points (from 30 windows in a group), and then every key. - is no record.

The planner reads that summary. A plugin the history marks crashed, or the daemon has quarantined, is left alone by the next plan with the reason history-crashed; one marked raises_xruns with history-xruns. Both are judged after the pin's rules (a history makes a plan more careful than the pin, never less) and before the cost. A plugin's cost is the larger of its qualification record's and its cpu_p95_solo (percent of one core, from the windows it ran alone). A plugin with no history is judged by its pin and its cost alone. With the history blocked or history_window_s 0 the plan is the pins' and the costs', and every member with nothing harder to say says history-unavailable.

A plan is made again by the daemon, never in the middle of a cycle of a worker, when a member of it is quarantined or its quarantine is cleared, and history_regroup_s seconds after a death that named no culprit and split a group, if no member of the plan has died since: the segments that did not change keep their workers, a group that was split is gathered, and the member the history marks goes alone. The new reasons come as a plan_reason event and in plan_get.

estimate <rate> <quantum> <uri> [<uri> ...] answers what a chain of those plugins would cost before any of them is added: a chain editor asks it before an insert. It loads nothing and moves nothing. The figures come from the qualification records of qualification_dir, the grid point at that rate and quantum: the latency is the measured frames, else the declared ones, added up; the CPU is the cost median in nanoseconds per sample times the rate, added up, as percent of one core's cycle. No per-worker overhead is added: none is measured. The RAM is the history's pss_mb_solo of each member, in bytes, and - unless every member has one. The workers are the segments plan would make of the members, so an isolated plugin counts a worker of its own. A member with no figure at that rate and quantum is counted and named by its position in the line, from 0, with -533 (no record names it), -534 (no point of the grid at that rate and quantum with a cost and a latency) or -535 (the uri names no plugin installed here, which plan would place nowhere); the latency and the CPU add up only the others, so a client says "not measured" for those members and never reads their figure as 0.

Four more words answer whether the chain fits in memory. ram_used_bytes is what the plugins running now hold, the Pss of every worker, - when one cannot be read. ram_added_bytes is what the members would add, from the memory of the qualification records at that rate and quantum: what instances of one plugin share is counted once in a segment, since a segment is one process, and again in another segment, which loads it again. ram_budget_bytes is the host's ram_budget_mb, - when none is set. ram_unknown_count is how many members have no figure: they add nothing to the sum and are not 0, and when no member has one ram_added_bytes is -:

estimate 48000 128 clap:/usr/lib64/clap/a.clap#org.example.a clap:/usr/lib64/clap/a.clap#org.example.b

What a worker must do

  • answer mod-host's protocol on -n -p <port> -f <port>, the feedback port opened by the daemon right after the command port;
  • print a line ending ready! on stdout once its socket accepts;
  • write, for state_save <dir>, files whose names begin effect_<instance> and read them back on state_load <dir>, skipping an instance with no file.

mod-host and omx-clap-host do.

Formats

The daemon holds its plugin formats in one table, src/formats.c, and nothing else in the daemon, the protocol or the pins names a format. A row says how a uri reaches the format (prefix, strip_prefix, fallback), which program serves it (worker), where its plugins are searched and how a worker's world is narrowed to one plugin (search, world_env, narrow_world), which files a pin holds (pin_collect), whether the worker checks the layout (layout_check), whether a pinned plugin must run in a worker of its own (pinned_own_only) and who answers the instance verbs (native_instance_verbs, else param_info). Adding a format is a row and its worker; formats_register refuses a row with a capability missing and says which. a test registers a third format in the test and takes it through add, param_set, pin_set and remove.

Who runs an LV2 plugin

lv2_worker chooses the program that runs LV2 plugins: auto (the default: the adapter first, mod-host for a plugin the adapter refuses, and for every add while omx-clap-host is not installed), omx-clap-host (the clap_host program, through its LV2 adapter, a plugin it cannot run refused with a code) or mod-host (the mod_host program). lv2_worker_set <uri> <mod-host|omx-clap-host|auto|-> overrides it for one plugin from then on, and - takes the override back. The two programs are two rows of the table, lv2 and lv2-clap, so policy_set, worker_env and worker_list name them like any format. The adapter row differs from the mod-host row in these ways, each held by a test:

capability lv2 (mod-host) lv2-clap (omx-clap-host)
worker mod_host clap_host, given the uri with its lv2: prefix
native_instance_verbs no: the daemon answers track_info, remote_pages, remote_page_get and param_info yes: the worker answers them from the plugin, and track_info is replayed to it after a respawn
layout_check no no: an LV2 pin holds the layout of the plugin's ports, not of the CLAP parameters the adapter presents, so pin_expect would refuse every pin plugin-qualify wrote
world_scope one bundle, narrowed: LV2_PATH holds a link to the plugin's bundle the same: the adapter opens bundles through the LV2 world
pin_pool no: a pinned plugin is placed own the same, for the same reason

An adapter handles a subset of LV2. When it refuses a plugin, the worker answers the add resp -102 <hosting code> (for instance hosting.features.midi-in-fed-empty, hosting.features.missing, hosting.topology.wider-than-strip or hosting.no-realisation). The add under omx-clap-host then answers -512 (LV2_ADAPTER_REFUSED) and the lv2_adapter_refused event carries that code, read from the reply to that add and never from the worker's log, which a pool worker shares with other plugins (- when the reply named none). Under auto the add is made again on the lv2 row, the plugin stays there, the event is sent once, and the controller never sees -512. The daemon remembers the refusal until the adapter has a reason to take the plugin again: lv2_worker_set of that uri (to any word, - included) forgets it, and so does a change of pins (pin_set, pin_accept, pin_clear) for every plugin; the next add under auto asks the adapter once more.

A plugin the adapter refused under auto runs on the lv2 row in a worker of its own, whatever the policy says, unless its add names a placement. The adapter never ran it, so nothing says it is safe in a shared worker. Some plugins abort in instantiate: drumkv1, samplv1 and synthv1 do, through Qt, when no display is set. Such a plugin takes down only its own worker. The add answers -102, and an instance_verb_dropped event names the add with its uri.

A plugin that no bundle of the worker's world holds is not a refusal: the worker answers resp -101 with no code. Under omx-clap-host the add answers that -101, with no event. Under auto the same add is made on the lv2 row, so mod-host looks for the plugin; nothing is remembered, and the adapter is asked again on the next add. Under auto an omx-clap-host that is not installed is not an error either: the add goes to the lv2 row.
