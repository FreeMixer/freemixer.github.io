Zynthian

Zynthian: plugin-hostd as its plugin host.

How to install it, how to use it, what it changes in Zynthian and where it stands. The method and every table are in the technical notes linked at the end.

01

What it is.

Zynthian is an open synthesizer and effects platform on a Raspberry Pi. It runs LV2 plugins through jalv, and through mod-host behind MOD-UI. plugin-hostd speaks mod-host's protocol and runs each plugin, LV2 or CLAP, in a worker process, so a plugin that crashes takes down only its own worker, which is put back with its settings. A whole chain can run in one worker instead of one process per plugin, and plugin-qualify measures each plugin on the device first, so the menus are built from what it found.

With it Zynthian gets a plugin-hostd engine beside jalv for LV2 and CLAP plugins in chains, plugin-hostd as a switchable replacement for mod-host under MOD-UI, plugin menus ordered and tagged from per-plugin qualification records, and chains whose plugins the daemon groups into as few workers as their pins allow.

02

How much it changes in Zynthian.

Nothing in Zynthian depends on it. It stays on jackd: no file that configures JACK changes, and no PipeWire is involved. As offered to Zynthian, the engine stays off until a user turns it on, and MOD-UI keeps mod-host until a user switches its backend; going back is the same setting.

FreeMixer's forks of zynthian-ui and zynthian-sys have it on: plugin-hostd is the default engine and MOD-UI's default backend, and the qualification sync is enabled. A plugin plugin-hostd refuses stays on jalv, listed in its menu, so nothing the user has disappears.

What runs when nobody uses it: the interface starts a daemon only when a chain holds a plugin-hostd plugin. What stays enabled is the qualification sync, two minutes after boot at the lowest CPU and disk priority, skipping every plugin whose files have not changed, and omx-panel's MOD GUI and complement syncs. All of them can be disabled; the first sync on a device with many plugins is long.

03

Install it.

The image

ZynthianOS Vangelis for the Raspberry Pi 4 and 5, with the forks of zynthian-ui and zynthian-sys, the OpenMixer apt repository, and plugin-hostd, omx-clap-host, omx-plugins, omx-panel and plugin-qualify installed and made the default. It is a release asset of FreeMixer's zynthian-sys fork, named after the upstream image and the fork's commit, with its sum and an inspection report in the release notes. It is larger than GitHub's limit for one asset, so it comes in parts:

# the image is published in parts: join them, check the sum, then flash
cat zynthianos-vangelis-omx.img.xz.* > zynthianos-vangelis-omx.img.xz
sha256sum -c zynthianos-vangelis-omx.img.xz.sha256

The first boot does what any Zynthian card does once: it detects the kit, regenerates the SSH keys and the web certificate, creates the Wi-Fi access point, grows the file system to the card, and reboots once. Two minutes after boot the qualification sync starts in the background, at the lowest priority, and does not hold the boot; with the qualification records package installed it only checks that the plugin files are the ones the records describe.

On an existing Vangelis

A Vangelis system already running needs no new image. As root, add the OpenMixer repository and install the packages:

curl -fsSLO https://www.openmixer.org/deb/openmixer-release.deb
sudo apt install ./openmixer-release.deb
sudo apt install plugin-hostd omx-clap-host omx-clap-scan omx-panel

openmixer-release carries the signing key and the apt source of the running Debian release. This enables no service: mod-host, MOD-UI, jalv and the menus stay as they were until you switch them.

Turn it on, and back off

Three settings, each undone by setting it back:

# the plugin engine: in /zynthian/config/zynthian_envars.sh, then restart the UI
ZYNTHIAN_PLUGIN_ENGINE=plugin-hostd
# MOD-UI's backend
set_modhost_backend.sh plugin-hostd
# plugins in series sharing one worker: in /zynthian/config/plugin-hostd.conf
grouping on

04

Use it.

With the plugin-hostd engine on, a plugin's menu entry ends in "(PH)". Select a chain, open its options and use Add Audio-FX processor; the plugin's controller pages follow its own sections.

A group: plugins in series in one worker

With grouping on, a run of plugins in series in a chain shares one worker process and one JACK client instead of one process each. A group is what the chain has in series with nothing between: a parallel slot, the mixer strip or a jalv plugin ends it. A processor that runs alone has a Grouping entry in its options saying why.

Grouping is off unless you set it. It saves most of the memory of one process per plugin: 24 plugins in one chain take about 64 MB, against about 110 MB under mod-host.

A channel strip as plugins

EQ and dynamics per chain are ordinary effects in that chain; Zynthian's mixer keeps its level, pan and sends. Either add separate plugins (omx keyed-gate, omx eq8, omx comp: you choose each one and its order, and eq8 has eight bands), or one plugin, omx strip: input trim, filters, a gate, four EQ bands and a compressor in stereo, in one load and one worker, its five stages in any order.

At 48 kHz and 512 frames, omx strip costs about 5.9 µs per block; omx eq8 and omx comp together about 11.4 µs, with eight EQ bands against four.

Shared effects on a Mixbus

One effect on a bus instead of one per chain, fed from each chain with Zynthian's own sends:

  1. Add a chain and choose Mixbus. In its options, Add Audio-FX processor: omx reverb, then omx delay, each "(PH)".
  2. In each chain that should feed it, open the mixer processor's controller page and raise the send level for that Mixbus, pre or post fader.

A plugin-hostd plugin behaves in a Mixbus as in any chain. A slot holds one processor or several, and several are parallel; a worker runs its plugins in series in one JACK client, so with grouping on:

Slots of the chainWhat runs
A, BA and B in one worker, one JACK client
A, [B, C]a worker each: B and C are parallel, three clients
A, B, [C, D], E, FA with B, a worker each for C and D, E with F: four clients
A, mixer strip, Ba worker each: the strip is in the signal's way
A, a jalv plugin, Ba worker each, and the jalv plugin's own client

Send levels, pre and post fader, and pinning or moving a Mixbus are Zynthian's mixer and chain manager: none of them sends anything to the daemon. Measured at JACK ports, series, parallel and Mixbus chains give the levels they should: unity in series, +6.02 dB for two in parallel, the strip's -20 dB where it sits.

05

The headline figures.

Measured on a Raspberry Pi 5 running Zynthian, at 48 kHz and 256 frames, read digitally at JACK ports, with plugin-hostd 0.15.9 and omx-clap-core 0.26.4, against Zynthian's own mod-host:

  • DSP load: a plugin-hostd chain has the lowest of the three hosts measured, 12.5 % for 24 plugins against 15.0 % for mod-host, with 0 xruns in every repeat.
  • Memory: 41 to 49 % less than mod-host, 64 MB against 109 MB for the 24.
  • Time to add: from cold, 24 plugins are ready in 0.55 s against 1.46 s; on a running host mod-host adds two plugins faster, and from four on the chain does.
  • Instruments: the same DSP load as mod-host, and about 43 MB less memory each.
  • Qualification: of 1602 plugins tried on the device, 1079 run in a shared worker and 306 in a worker of their own.

06

Where it stands.

Proven on the device

  • The plugin-hostd engine runs Zynthian chains, LV2 and CLAP side by side, with the plugin menus built from the qualification records.
  • Controller pages follow the plugin's own sections and are named by what they hold.
  • Instruments and effects play through the engine, read digitally at JACK ports with 0 xruns; factory and user presets load.
  • Grouping through Zynthian's own engine passes its proof: a run in series groups as one client, and a parallel slot, the strip or another client ends it.
  • A lost worker comes back: after a killed worker, the daemon puts it back with its settings and the links it made itself in about 350 ms.

Released, to be checked on the device

  • Every plugin call saves and checks the registers a function must keep; a plugin that changes one is moved to a worker of its own.
  • A chain shares one JACK client per worker, and a mono plugin runs inside a stereo chain.
  • Plugins are added straight into a chain's worker, which is what makes a chain faster to build than mod-host.

Still open

  • Chains built from Zynthian's menu with grouping on, measured as the daemon's chains were.
  • A listening test through the audio interface: the figures so far are read digitally at the JACK ports.
  • Preset listing and loading for every instrument from the menu, and on CLAP.
  • The round trip of a snapshot that holds a plugin-hostd instrument.
  • Mixbus chains and parallel slots measured with Zynthian's own mixer in the path on the device.

07

Where the changes to Zynthian stand.

The engine and the system changes are carried on FreeMixer's forks of zynthian-ui and zynthian-sys. In zynthian-ui: the plugin-hostd engine, plugin-hostd by default with a snapshot converter, menus from qualification, chains from the daemon's planner. In zynthian-sys: the OpenMixer repository, plugin-hostd as the mod-host of MOD-UI, MOD GUIs from omx-panel, OpenMixer in the default install. Merged and open pull requests are listed on each fork.

Upstream, one change is proposed so far: building MOD-UI's environment on Python 3.13, in zynthian-sys. The rest has not been proposed to Zynthian's maintainers yet.
